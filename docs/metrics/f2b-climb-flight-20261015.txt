THE CLIMB LEG, FLOWN; THE B1 WINDOW, FIXED; AND THE PLAN OVERLAY, RESTORED
================================================================================
Written 2026-10-15 by the round that fixed the climb leg's arming rule.  Commit under this file:
"plan: the climb leg's clock armed ON THE PAD" is the fix; this file is the flight that proves it, plus two
instrument repairs the same flight exposed.  Every number is copied from the run's own files and names its
denominator; the run directories are named next to each block.

3. B1'S WINDOW: THE SETPOINT-DRIVEN TAKE-OFF PUT THE PAD INSIDE THE BOX
-----------------------------------------------------------------------
`RECT34-accept` first read "B1 ... E 2.584 m  N 1.651 m" -- a bigger jump than any flight-quality change
in this project's history, and it is not a flight-quality number.  `tools/metrics.py` opened the box at
`t_sim_all[leg_idx[1]]`, the entry of the SECOND leg phase, and that index was chosen when the tour's first
leg phase WAS the pad->corner-1 transit (the code's own 2026-10-13 note records the pad being excluded on
purpose, after it had produced "2.54 x 1.57 m for a 2.0 x 1.2 m square").  A climb leg in front of the tour
moves every phase by one: leg1 = the climb, leg2 = the transit, and the same index opened the window AT
THE PAD, 0.64 m outside the rectangle.

THE RULE NOW, in the aircraft's own terms: the window opens at the first leg phase whose recorded truth
position (`phase.csv` `truth_x`/`truth_y`) is within 0.15 m of the tour's entry corner -- the same 0.15 m
`tools/dwell-audit.py` and B1's corner-visit companion already use for "the aircraft is at this corner".
`_stage/b1-window-ab.py` computes both rules on every sortie (`E / N` in metres, extent; delta in mm):

NO BOUND MOVED: 2.10 / 1.30, unchanged, and `RECT34-accept` still FAILS both axes.  The historical numbers

<= 50, ...)" -- a label saying three rows failed above a parenthetical showing two of them passing.  It now
names the rows that actually failed ("A1/A2/B1 FAIL: B1   (...)"); the parenthetical keeps its exact shape
for the batch summary.


4. THE PLAN OVERLAY, RESTORED (`tools/plot-run.py`)
---------------------------------------------------
`tools/plot-run.py` printed "6451 Path messages, 0 distinct plans drawn" on every F2 recording, and the
RECT26 figure says so in its own caption.  The join key was the bug: the old `nav_msgs/Path` recorder wrote
`points.csv.t_us` as the stamp of the Path MESSAGE, while the `PositionCommand` recorder writes the stamp
at which that leg's target was FIRST commanded -- exactly `traj.csv.t0_us`.  The plotter now joins on
`t0_us` (falling back to the message stamp, so an old run still draws) and marks the COMMANDED WAYPOINTS
themselves, from `traj.csv.cmd.csv`, because the plan's output is a sequence of waypoints and not a path:
`RECT33-accept` reads "plans: 6881 Path messages, 6 distinct plans drawn (points in W)" and
"commanded waypoints: 6 distinct targets in 6881 messages -- w1 (0,0,2.5), w2 (0.5,0.4,2.0), ...".
On RECT33 two of those six legs are degenerate BY CONSTRUCTION: the climb is `n=1` point (no horizontal
extent) and the tour's entry leg is the pad->corner-1 diagonal.
