FLIGHT D -- PRE-REGISTRATION: THE ACCELERATION GOES ON THE WIRE  (2026-10-16, written before arming)

THE OWNER'S INSTRUCTION: "Mask 改好,a 也要" -- send the acceleration feed-forward too.

WHAT CHANGES, AND ONLY THIS: `BRIDGE_FIELDS=posvelacc`, i.e. the MAVLink `type_mask` goes from
`POS_VEL_YAW_MASK` (2496 = position+velocity+yaw, with AFX/AFY/AFZ set to IGNORE, `mavlink_impl.py:55`) to
`POS_VEL_ACC_YAW_MASK` (**2048 = IGNORE_YAW_RATE only**, `:57`), so the acceleration column that has always been
in the message is finally used by the flight controller.  Everything else is Flight C, which is the first run in
this investigation that never entered a pillar: the cleaned tree (928 added lines over 6 files after
`_stage/apply-cleanup1.py`), H1 (the FSM checks the vehicle), H2 (the safety re-commit is tagged), the 0.35 m
reference clamp, the raised flight-controller limits, the plan's own heading, and `EGO_MAX_VEL=0.8` /
`EGO_MAX_ACC=1.0`.

WHY THIS IS WORTH DOING NOW, WHEN IT WAS REFUTED BEFORE.  `posvelacc` was refuted by DIAG33, which ABORTED on the
geofence with the reference acceleration alternating at 22 m/s² -- because the age rule was jumping the sampled
point and differentiating across the jump.  Three things have changed since: the reference is clamped to 0.35 m
(a measured max step of 0.3576 m against 0.9945 m), the plan's own acceleration ceiling is 1.0 m/s² instead of a
soft 3.0, and the flight controller's shaper limits are raised (WP_ACC 2.5 -> 6.0, `PSC_NE_JERK` 5 -> 30,
`ATC_ANGLE_MAX` 30 -> 40 deg) so it can actually act on what we send.  The point of the arm is that the FCU's
acceleration-limited reference model has been *reconstructing* an acceleration it was never given; with the mask
open it is given the plan's own.
