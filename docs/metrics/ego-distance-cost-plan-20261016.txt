=== QUESTION 1, MADE EXACT: WIRING THE DISTANCE COST TO THE LAUNCH PARAMETERS ======================
The first flight of the term used a LOCAL CONSTANT (`lambda_collision = 0.5`) because the build refused
`node->get_parameter(...)` with `'node' was not declared in this scope` -- and the reason is now known, read from
the header: **the node handle is a PARAMETER of the initialiser, not a member**:

    bspline_optimizer.h:95     void setParam(rclcpp::Node::SharedPtr node);

and `dist0_` -- which the same style of call sets (`node->get_parameter("optimization/dist0", dist0_);`, seen at
`bspline_optimizer.cpp:28`, inside `setParam`) -- IS a member, which is why `cps_.clearance = dist0_` compiles
inside the class and the parameter read does not.  So the wiring is three lines, and they are known:

  1. in the class (bspline_optimizer.h, beside the other members):
         rclcpp::Node::SharedPtr node_;          // the handle setParam is given, kept so cost terms can read
  2. in setParam, where the other parameters are read:
         node_ = node;
  3. in `calcFieldDistanceCost`, replacing the constant:
         double lambda_collision = 0.5;
         node_->get_parameter("optimization/lambda_collision", lambda_collision);

WHY IT MATTERS RATHER THAN BEING COSMETIC: with the constant, the launch file's `optimization/lambda_collision`
and `optimization/dist0` STILL multiply nothing, so the flown term was "the shape with 0.5 / 0.5" and the two

makes `dist0` mean what upstream's name says for the first time.

AND THE OTHER TWO QUESTIONS, unchanged and still open: whether the `rc=1` of the term's one flight was the term
destabilising the optimiser (a term that does that would show exactly this way, and it is the first thing to look
at), and whether the 0.20 m footprint is the right bar for this planner on this mission.

=== WHERE A FAILSAFE'S TRACE WOULD HAVE TO GO (round 58): A REFUSED PATCH AND A POINTER ==============
Item 4 of the handoff says a failsafe must leave a trace WHEN IT HAPPENS -- DIAG29's entire cause survived only
as one teardown line that my own grep had truncated.  `_stage/trace-statustext.py` was written to add one
timestamped log line at the FCU-text site, with the same refuse-unless-certain rule the field patches used, and
**it refused and changed nothing** -- correctly, because the guess was wrong about the mechanism:

    grep -n 'STATUSTEXT|statustext|text' src/supervisor/supervisor.py
      17:  * its OWN endpoint -- heartbeat/position age, armed, mode, landed_state, statustext.
     436/464:  return "arming refused: %s" % _texts(self.bridge.state())
     676:  self.log("the FCU's last words: %s" % _texts(st))
     684:  def _texts(st):

There is **no literal STATUSTEXT site in the supervisor**: the FCU's text is carried inside the BRIDGE's state
(`self.bridge.state()`), accumulated, and printed only at teardown through `_texts(st)`.  So the instrumentation
belongs one layer down -- where the bridge appends to that state as MAVLink STATUSTEXT messages arrive -- and the
supervisor's `:676` is the consumer, not the source.

WHAT THIS ROUND LEAVES: no change to any file (the script's refusal is the record), a pointer to the right layer
for item 4, and one more instance of the pattern this project has used to avoid half-applied work: **a patch
script that refuses when its assumption is not confirmed by the file itself**.

=== CORRECTION OF ROUND 58's POINTER: THE FCU'S TEXT IS NOT IN OUR BRIDGE AT ALL =====================
Round 58 concluded that the when-it-happens trace belongs "one layer down, in the bridge".  That was right about
the LAYER and wrong about the FILE.  A second refused patch (`_stage/bridge-text-trace.py`) searched
`src/bridge/bridge_node.py` for every plausible name and found NOTHING:

    grep -n 'STATUSTEXT'   -> (none)
    grep -n 'statustext'   -> (none)
    grep -n '253'          -> (none)
    grep -n 'text'         -> (none)

`bridge_node.py` never sees the FCU's text.  The supervisor's own docstring says why (line 17): it has

    "its OWN endpoint -- heartbeat/position age, armed, mode, landed_state, statustext"

so `self.bridge.state()` is the SUPERVISOR'S OWN MAVLink connection (its tcp:5761 endpoint, class 76, which this
project has always described as "the supervisor's own channel"), not the class-84 bridge that owns the setpoint
stream.  **The trace therefore belongs in the supervisor's own MAVLink client** -- wherever `self.bridge` is
implemented inside `src/supervisor/` -- and that is where the next round should look.

Two refused patches in a row, both leaving the tree untouched: the rule is doing what it was built for.  And the
correction is the third time this project has mistaken one component for another (the published visualisation for
the planner's buffer, `traj.csv` for `traj.csv.points.csv`, and now the class-84 bridge for the supervisor's own
MAVLink link) -- each caught by asking the artefact itself rather than trusting the reasoning that pointed at it.
